# Design Discussion: Compile-Time Stored-Procedure Mapping

**Status:** Preliminary / brainstormed architectural direction  
**Purpose:** Directional handoff for detailed design and implementation  
**Scope:** Core architecture, ownership boundaries, data flow, and constraints

## 1. Direction

Replace the stored-procedure mapping subsystem's runtime IL/expression-tree compilation with a **single Core-owned source-generation pipeline**.

The central boundary is:

> **Core owns stored-procedure ORM structure and execution orchestration. Providers own provider-specific configuration semantics and runtime implementation.**

The Core generator must not acquire semantic knowledge of provider-specific database types, readers, conversions, parameter construction, or other provider internals.

Provider assemblies instead expose:

1. their normal consumer-facing fluent configuration API;
2. a structurally discoverable **provider grammar** describing the supported provider-specific configuration operations;
3. ordinary compiled helpers/intrinsics implementing the provider-specific runtime behavior selected by that grammar.

The generator inspects provider declarations symbolically through Roslyn. It does not load or execute provider code inside the analyzer process.

The design specializes the CESI, CTCD, and CTSB patterns documented in [roslyn-patterns](../roslyn-patterns/README.md).

## 2. Core and Provider Ownership

### Core

Core (library + generator) understands only the fixed ORM topology and behavior required for execution, including:

- procedures/functions;
- I/O container members and parameters;
- logical parameter direction where required for orchestration;
- result/no-result mappings;
- single versus collection results;
- result columns and target members;
- execution lifecycle, generated-plan registration, and invocation.

Core also owns the **provider meta-grammar**: discovery of provider grammars, grammar scopes, terminal operations, nested/sub-builder transitions, supported compile-time argument forms, symbolic state threading, finalization, validation, and generic source lowering.

### Providers

Providers own:

- provider-specific fluent builder APIs;
- the structural grammar describing those APIs;
- opaque provider configuration state;
- provider-specific parameter construction and output handling;
- provider-specific result reading/conversion;
- provider-specific validation/normalization;
- arbitrary complex implementation algorithms;
- the callable intrinsics ABI used by generated consumer code.

Provider complexity and behavior of intrinsics stay in ordinary compiled C#. The grammar describes **which operations apply and how they compose**, not how provider algorithms are implemented.

## 3. Consumer Configuration and Discovery

The existing fluent `Configure(...)` style remains the declaration surface, but its syntax tree may be intentionally restricted to a subset of statically analyzable operations. For example:

```csharp
public static void Configure(MySqlProcedureBuilder<...> procedure)
{
    procedure.Parameter(x => x.Value)
        .HasDbType(MySqlDbType.Int32)
        .HasSize(32);

    procedure.Returns<Result>()
        .AsCollection()
        .Column(x => x.Id)
        .GetAsInt32();
}
```

The generator treats `Configure` as a **restricted declarative source DSL** that is **statically interpreted** by the generator to emit a corresponding fixed procedure plan. In the fully source-generated model, the `Configure()` method is **never executed at runtime**. Runtime functionality of the builder API will be kept for self-documentation and comparative testing, but the generator must not rely on runtime execution of the builder API to produce a valid plan.

- Core-owned operations update the procedure's structural model (mirroring the flow of the declared builder API) and are lowered into generated source.
- Provider-owned operations are matched against the active provider grammar.

Only statically interpretable syntax is expected to be supported. Arbitrary runtime-dependent configuration must be diagnosed rather than executed or silently interpreted at runtime.

Configuration source is analyzed in the compilation where it is declared. Procedures compiled into another assembly must carry their generated plan with them; downstream generators must not attempt to reconstruct referenced `Configure()` method bodies from metadata.

## 4. Provider Grammar and Symbolic State

A provider grammar describes a typed configuration pipeline over an opaque provider-owned state:

```text
Initialize
    Core context -> TState

Terminal
    TState + compile-time configuration arguments -> TState

...

Finalize / Build
    TState + runtime inputs -> provider runtime object/value
```

`TState` is opaque to Core. It may represent an actual ADO.NET object, a configuration descriptor, a builder struct, or any other provider-defined representation.

Core only validates and threads this state symbolically.

Illustrative example (APIs subject to change/pseudocode):

```csharp
[ParameterGramma<MySqlIntrinsics>(
    StateInitializer = nameof(MySqlIntrinsics.CreateParameter),
    StateFinalizer = nameof(MySqlIntrinsics.BuildParameter))]
class MySqlParameterGrammar
{
    [TerminalIntrinsic<MySqlParameterIntrinsics>(nameof(MySqlParameterIntrinsics.HasDbType))]
    public static MySqlParameterBuilder HasDbType(MySqlParameterBuilder b, MySqlDbType type);

    [CompositeIntrinsic<MySqlParameterIntrinsics>(nameof(MySqlParameterIntrinsics.HasSize), SubGrammar = typeof(MySqlSizeGrammar))]
    public static MySqlParameterBuilder HasSize(MySqlParameterBuilder b, Action<MySqlSizeBuilder> configure);
}
```

where the provider grammar structurally describes the provider's fluent API (maybe it makes sense to put those annotations on the builder methods themselves?). The complexity of the provider grammar structure is **bounded** by Core's meta-grammar: Composite nested builders, terminal operations, initializer/finalizer of provider state, and compile-time argument forms are (at least) supported.

For example:

```csharp
parameter.HasDbType(MySqlDbType.Int32)
       .HasSize(size => size.SomeBuilderMethod(...));
```

may conceptually lower to:

```csharp
...
// create arbitrary builder state
global:: MySqlProviderNamespace.ProviderSpecificState state = MySqlIntrinsics.CreateParameter();
// convention-based set of supported intrinsics signature and argument forms
state = MySqlParameterIntrinsics.HasDbType(state, MySqlDbType.Int32); // compile-time constant
state = ...// decompose the composite builder call into a sequence of terminal intrinsic calls
// parameter here must be whatever ADO.NET/other type the MySQL runtime expects
var parameter = MySqlIntrinsics.BuildParameter(state, runtimeValue, ...);
...
```

The architecture does **not** require this exact runtime shape. The provider may collapse, optimize, or otherwise finalize the symbolic configuration however it wants.

The mandatory finalizer is the main complexity boundary: intermediate terminals may merely accumulate settings, while `BuildParameter()` or an equivalent provider-owned operation performs validation, defaulting, specialization, and construction.

The same general model applies to result-column configuration, type conversion, and other provider-specific operations. Final generated code should directly invoke provider-owned reader/conversion helpers rather than recreate runtime expression trees or delegate graphs.

For this to work, the core generator must have (some, minimal) understanding/expectation of the overall invariants (e.g., initialize some state, configure it, finalize it to produce a runtime object/value).

## 5. CTSB / Runtime Helper Boundary

The provider grammar is a specialized Compile-Time Static Binding (CTSB) application:

```text
consumer configuration terminal
    -> provider grammar operation
    -> callable provider symbol
    -> generated static invocation
```

The generator resolves operations through Roslyn symbols only and acts as a static linker between consumer configuration and provider intrinsics.

Arbitrarily complex behavior remains behind provider-owned compiled helpers:

```csharp
ProviderSpecificState MySqlParameterIntrinsics::HasDbType(ProviderSpecificState state, MySqlDbType dbType)
{
    // Arbitrarily complex provider implementation.
}
...
public static Target OracleResultReaderIntrinsics::ReadComplexType(
    ProviderReader reader,
    int ordinal,
    ProcedureRuntimeContext context)
{
    // Arbitrarily complex provider implementation.
}
```

The generator only needs to validate that the symbol can be called and emit the invocation.

Compile-Time Contract Discover (CTCD) remains appropriate for singular infrastructure roles that must resolve to exactly one symbol. CTSB/provider grammar handles extensible conditional behavior.

Alternatively, core meta-grammar symbols could be defined in a shared code project, but that code would have to be inlined into the generator and all providers during compilation, since Roslyn cannot reliably load additional assemblies into the analyzer process.

## 6. Generated Runtime Shape

The generated output should be a coarse static procedure plan rather than a generated reconstruction of today's compiler object graph:

```text
GeneratedProcedurePlan
    Create/BindParameters(...)
    StoreOutputs(...)
    ReadResult(...)
    execution metadata
```

Generated code should be straightforward statically bound C# using direct provider helper/intrinsic calls.

Core runtime remains responsible for command/connection orchestration, parameter ownership, sync/async execution, result iteration/cardinality, disposal, and generated-plan lookup.

The Core generator may emit IO container member binding/accessors or require a well-defined shape of IO / result object (e.g., settable properties, `with`-style mutation, or factories).

Provider helpers construct/read/convert provider-specific objects but should not assume ownership of Core-managed execution resources.

## 7. Architectural Invariants

The detailed design must preserve these boundaries:

- **Provider-semantic agnosticism:** adding a regular provider capability must not require a new provider-specific switch or vocabulary entry in Core, unless Core meta-grammar must be extended.
- **No analyzer-time provider execution:** providers are inspected through Roslyn symbols only.
- **Opaque provider state:** Core understands the state-transition contract, not the state's meaning.
- **Compiled provider algorithms:** complex implementation stays in provider C# intrinsics, not in the grammar DSL.
- **Static generated linking:** source generation must replace runtime metaprogramming, not generate another runtime expression/delegate system.
- **Deterministic grammar resolution:** malformed, conflicting, or ambiguous grammar/binding states must be diagnosed deterministically.
- **Normal accessibility:** generated code calls only legally accessible provider symbols; provider internals stay behind a narrow callable facade.
- **Core owns orchestration semantics:** provider-specific representation belongs to providers; behavior affecting how Core executes a procedure remains a Core concern.

Existing behavior such as output-member assignment, constructor selection, nullable/`DBNull` handling, provider-specific conversions, function/return-value handling, result cardinality, and resource lifetime must be covered during migration/parity testing. These cases should validate the boundary rather than expand Core's provider vocabulary.

## 8. Target Data Flow

```text
Consumer procedure declaration
        |
        v
static Configure(builder) -> analyzable Roslyn syntax tree with known (subset of) supported operations
        |
        v
Core target/configuration discovery
        |
        v
Core structural interpretation
        |
        +-- Core operation -> update procedure topology/model
        |
        `-- Provider operation
                |
                v
        Provider grammar lookup
                |
                v
        Symbolic provider-state transitions
                |
                v
        Provider finalization / resolved helpers
                |
                v
        Bound procedure generation model
                |
                v
        Generic Core source emission
                |
                v
        Generated static procedure plan
                |
                v
        Core runtime orchestration
                |
                v
        Provider ADO.NET implementation
```

## 9. Handoff Directive

The next phase should refine the concrete grammar representation, supported `Configure()` syntax subset, intermediate models, diagnostics, generated-plan interfaces, registration/bootstrap mechanics, and migration strategy without changing the macro-level boundary established here.

The design should prefer the smallest meta-grammar capable of expressing the existing Core, MySQL, and Oracle behavior.

The principal success criterion is:

> **A future provider can introduce an obscure database type with arbitrarily complex parameter or result handling by defining its fluent grammar and ordinary compiled implementation helpers, without requiring provider-specific changes to the Core generator or additional provider-specific generator assemblies.**
